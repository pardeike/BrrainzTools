- Proactively check provider allowance with `brrainztools usage codex` or `brrainztools usage claude` at the start of substantial work, before parallel agents, and after a usage-limit interruption. Use `brrainztools usage all` when coordinating both providers. During sustained work, poll at meaningful checkpoints and at least every five minutes. At 5% or less in any applicable window, poll at least every minute and before another substantial operation. Poll at the next opportunity after blocking work. Read `data.providers[].status`, applicable `windows[].remainingPercent` and `resetsAt`, and Codex `credits.status`, `credits.balance`, `credits.overageLimitReached`, and `credits.canContinue`. A fresh successful Codex poll with `credits.status == "ok"` and `credits.canContinue == true` permits continued work against the existing credit balance, even when account-wide `primary` or `secondary` allowance is at or below 1% or its forecast predicts exhaustion. This permission does not cover model-specific limits, provider restrictions, unknown or stale data, API billing, new credit purchases, or automatic reload. Subscription forecasts describe subscription exhaustion, not exhaustion of the credit balance. Without verified usable Codex credits, stop substantive work and affected sub-agents when any applicable window reaches 1% or less. Claude retains the same 1% stop rule. Always stop for a model-specific window at 1% or less. Resume only after a fresh poll confirms sufficient applicable allowance or usable Codex credits, or an explicit user override. If credit status is missing, malformed, restricted, zero, or negative, do not assume credit-backed continuation. Normal subscription work may continue while its allowance is sufficient. On HTTP 429, back off. If neither allowance nor credit-backed continuation can be established, pause substantial work and give a brief handoff. Never enable automatic purchases or change provider billing authentication for this policy. These are shared account allowances and credit balances, not per-agent token budgets; polling cannot reserve capacity.
- In Codex sessions where the Codex Computer Use tool (`computer-use` MCP/plugin) is available, prefer it over BrrainzTools for interactive macOS desktop work: looking at the screen, clicking, typing, scrolling, dragging, and driving app UI. There, use `brrainztools` for what Computer Use does not cover (subscription usage polling, permission diagnostics, scripted launch/quit/open-file/wait steps, read-only AX or menu tree inspection, clipboard, saved capture files) or as the fallback when Computer Use is unavailable or fails. The BrrainzTools preferences below apply in that order.
- Otherwise, use the `brrainztools` skill and the `brrainztools` command on PATH as the preferred project tool for macOS desktop automation: screenshots, running-app discovery, desktop app/window/menu inspection, visible-window fallback capture, AX window listing/raising, in-window crops, menu capture, occluded-window capture, Accessibility-driven UX actions, app launch/quit/activation, semantic document opening, keyboard/mouse input, clipboard, waiting, and window management.
- Prefer `brrainztools --help` and `brrainztools <subcommand> --help` for exact command syntax instead of guessing or using raw `screencapture`, System Events AppleScript, or generic screenshot tooling first.
- Use BrrainzTools app discovery when the exact app name is unknown. If ScreenCaptureKit app/window capture fails or visible pixels are enough, use visible-window listing/capture before raw rectangle capture. If Screen Recording permission blocks app/window inspection but Accessibility works, use `brrainztools ax --app APP windows` and `brrainztools ax --app APP raise --window-index N` before AppleScript fallbacks.
- Use BrrainzTools menu-bar modes for menu-bar/status-item menus or popovers from accessory/background apps; use read-only `brrainztools menu --app APP tree` to inspect nested menu state/actions without opening menus or activating the app, and `brrainztools menu --app APP press-item TEXT` to choose child items inside status menus; use rectangle capture only for visible UI that is not exposed through app/window/visible-window/menu-bar commands.
- For local app development loops, prefer BrrainzTools primitives such as `brrainztools launch PATH|BUNDLE_ID --wait-window`, `brrainztools open-file DOCUMENT --app PATH|BUNDLE_ID --wait-window` for document handoffs, `brrainztools quit --app APP --wait` before an immediate relaunch, `brrainztools reveal PATH`, `brrainztools ax --app APP wait-for-element ...`, `set-value`, `type`, `key`, `click`, `drag`, `scroll`, `move`, `resize`, `close`, `minimize`, `brrainztools doctor`, and `brrainztools clipboard` before ad hoc sleeps or AppleScript.
- If System Events AppleScript seems necessary for screenshot/UX work, first treat that as a BrrainzTools capability gap: report the use case and suggest the BrrainzTools improvement before using the fallback.
- BrrainzTools is maintained by this project; if it has a bug or missing capability, report the concrete use case and suggest a tool improvement instead of silently accepting the limitation.
- BrrainzTools was formerly named RegionShot; treat `regionshot` references in older notes, logs, or scripts as stale and use `brrainztools` instead.
